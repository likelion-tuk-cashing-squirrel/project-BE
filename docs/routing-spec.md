# Routing Component Spec

## 목적

다국어 요청을 받아 LLM 호출 전 최적 처리 경로를 결정하는 라우터.
비영어권 언어는 토큰화 효율이 낮아 동일 의미의 문장도 영어 대비 2~3배 토큰을 소모한다.
이 컴포넌트는 요청마다 **어떤 처리 경로를 탈지** 판별해 뒤쪽 파이프라인에 알려준다.

## 위치

전체 파이프라인의 STEP 01. 오케스트레이터가 요청 수신 직후 이 컴포넌트를 호출하고,
반환된 `RoutingResult`에 따라 이후 단계(마스킹 → 피벗 → LLM → 재번역)를 분기시킨다.
이 컴포넌트는 **판단만 하고 텍스트를 변형하지 않는다.**

## 기술 스택

- Java / Spring Boot
- 토큰 계산: JTokkit (`EncodingType.O200K_BASE` 명시 필수 — 기본값이나 CL100K 쓰면 안 됨)
- 언어 감지: 자바 언어 감지 라이브러리 (optimaize/language-detector 등)

## 핵심 요구사항

### 1. RoutingTier enum

```
SKIP    // 임계치 미만. 마스킹/피벗 전부 생략, 바로 LLM 호출
TIER_1  // 영어. 피벗/재번역 불필요
TIER_2  // 베트남어 등. 영어 피벗 + 재번역 필요
TIER_3  // 필리핀어(타갈로그). 형태소 힌트 주입 + 피벗 + 재번역 필요
```

boolean(isPivot) 대신 enum을 쓰는 이유: 분기가 4가지이며,
TIER_3는 별도 형태소 분석 마이크로서비스를 추가 호출해야 하므로 구분이 필요하다.

### 2. RoutingResult DTO

```
RoutingTier tier
String detectedLanguage   // ISO 639-1 코드 (en, vi, tl 등)
int estimatedTokens       // JTokkit o200k_base 기준 원문 토큰 수
double confidence         // 언어 감지 신뢰도 (0.0 ~ 1.0)
```

### 3. TokenCalculator

- 입력: 텍스트 문자열
- 출력: o200k_base 기준 토큰 수
- Encoding 인스턴스는 매 호출마다 생성하지 말고 재사용 (초기화 비용 큼)

### 4. LanguageDetector

- 입력: 텍스트 문자열
- 출력: 언어 코드 + 신뢰도
- **짧은 텍스트에서 오판 가능성 있음.** 신뢰도가 임계값 미만이면
  `TIER_1`(영어 취급, 가장 안전한 폴백)로 처리
- 매핑: `en → TIER_1`, `vi → TIER_2`, `tl → TIER_3`, 그 외 → `TIER_1`

### 5. CostRouter

판별 순서:
1. 토큰 수 계산
2. 토큰 수가 임계치 미만이면 → `SKIP` 반환 (언어 감지 생략 가능)
3. 임계치 이상이면 언어 감지 → 매핑 테이블로 TIER 결정
4. 신뢰도 낮으면 `TIER_1`로 폴백

임계치 값은 하드코딩 금지. `application.yml`의 설정값으로 주입받을 것.
(실측 데이터로 조정할 예정)

## 테스트 케이스

| 입력 | 기대 결과 |
|---|---|
| 짧은 영어 인사말 | SKIP |
| 짧은 베트남어 문장 | SKIP |
| 긴 영어 문단 | TIER_1 |
| 긴 베트남어 문단 | TIER_2 |
| 긴 필리핀어 문단 | TIER_3 |
| 이모지/숫자만 | TIER_1 (폴백) |
| 빈 문자열 | 예외 처리 또는 SKIP |

---

## 하지 않을 것 (스코프 밖)

- 텍스트 변형 (마스킹, 번역, 형태소 분석) — 다른 컴포넌트 담당
- LLM 호출 — 오케스트레이터 담당
- 실제 비용(원화/달러) 계산 — 대시보드 담당. 여기선 토큰 수만 반환
